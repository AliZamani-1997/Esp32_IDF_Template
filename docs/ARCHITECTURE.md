## ۵) معماری چندلایه

کد در چهار لایه سازمان می‌یابد. **جهت وابستگی همیشه رو به پایین است** و هرگز
برنمی‌گردد. قاعده‌ی کامل در `docs/CODING_STANDARDS.md` بخش ۱.

```
┌──────────────────────────────────────────────────────────────────┐
│ L4  app        main/            app_main، منطق برنامه            │
│                depends on: core, rtos, drivers                   │
├──────────────────────────────────────────────────────────────────┤
│ L3  drivers    components/drivers/                               │
│                Gpio · Uart · I2cMasterBus/I2cDevice ·            │
│                SpiBus/SpiDevice · NvsHandle                      │
│                depends on: core  (+ rtos در صورت نیاز)           │
├──────────────────────────────────────────────────────────────────┤
│ L2  rtos       components/rtos/                                  │
│                Task · Mutex + LockGuard · Queue<T>               │
│                depends on: core                                  │
├──────────────────────────────────────────────────────────────────┤
│ L1  core       components/core/                                  │
│                Error/Result/Status + CORE_TRY_* · CORE_LOG* ·    │
│                Timer · detail/ticks.hpp                          │
│                depends on: هیچ‌کدام از لایه‌های پروژه             │
├──────────────────────────────────────────────────────────────────┤
│      ESP-IDF / FreeRTOS — کد سی که فقط رَپِرها می‌بینند          │
└──────────────────────────────────────────────────────────────────┘
```

| لایه | کامپوننت | مسئولیت | وابستگی‌ها | وضعیت |
|---|---|---|---|---|
| ۱ | `core` | پایه: خطا، لاگ، زمان | `esp_common`, `log`, `esp_timer`, `freertos` | ✅ |
| ۲ | `rtos` | رَپِر FreeRTOS | `core`, `freertos` | ✅ |
| ۳ | `drivers` | رَپِر پریفرال‌ها | `core`, `esp_driver_gpio/uart/i2c/spi`, `nvs_flash` | ✅ |
| ۴ | `main` | برنامه | `core`, `rtos`, `drivers` | ✅ |
| — | ⬜ کامپوننت‌های دامنه | ⬜ پس از فاز ۱ — بالای `drivers` | لایه‌های پایین‌تر | ⬜ |

> **قاعده‌ی طلایی:** کد برنامه **هرگز** مستقیم `esp_*` / `gpio_*` / `xTask*` صدا
> نمی‌زند. همه چیز از رَپِرها می‌گذرد. این تنها راهی است که بشود بعداً درایورها
> را عوض کرد.

> **چرا کامپوننت FreeRTOS اسمش `rtos` است و نه `freertos`:** ESP-IDF خودش
> کامپوننتی به نام `freertos` دارد و نام‌ها باید یکتا باشند. `REQUIRES freertos`
> کد سی ESP-IDF را می‌آورد؛ `REQUIRES rtos` لایه‌ی ما را.

> **چرا لایه‌ی برنامه در پوشه‌ی `main/` است و نه `app/`:** ESP-IDF الزام می‌کند
> کامپوننتی که `app_main` را تعریف می‌کند `main` نام داشته باشد. تغییر نامش یعنی
> دست‌کاری `COMPONENT_DIRS` که ارزشش را ندارد.

| rtos | `mutex.hpp` | `Mutex`, `LockGuard` | `xSemaphoreCreate*` |
| rtos | `queue.hpp` | `Queue<T>` (فقط هدر) | `xQueue*` |
| rtos | `rtos.hpp` | هدر چتر لایه‌ی ۲ | — |

| drivers | `drivers.hpp` | هدر چتر لایه‌ی ۳ | — |

### قواعدی که هر رَپِر رعایت می‌کند

1. **غیرقابل کپی، قابل جابه‌جایی** (`= delete` برای کپی، move سازنده و move assignment).
2. **مخرب همه چیز را آزاد می‌کند** — پین، هندل باس، نصب درایور، تسک، تایمر، هندل NVS.
3. **move assignment اول منبع فعلی را آزاد می‌کند**، بعد می‌دزدد.
4. **ساخت یک منبع، تابع کارخانه‌ای `static` است که `core::Result<T>` برمی‌گرداند** — نه سازنده.
   چون سازنده در این پروژه نمی‌تواند شکست را گزارش کند.
5. **`release()`** هندل خام را پس می‌دهد و شیء را بی‌اثر می‌کند.

روند گام‌به‌گام افزودن رَپِر جدید در `.workbuddy-ai/skills/cpp-wrapper-layers/`.

### قالب ساخت کامپوننت جدید

```
components/<name>/
├── CMakeLists.txt
├── include/<name>/         ← رابط عمومی (تنها چیزی که بقیه می‌بینند)
└── src/                    ← پیاده‌سازی
```

```cmake
idf_component_register(SRCS "src/<module>.cpp"
                       INCLUDE_DIRS "include"
                       REQUIRES <deps>)
```

> فراموش کردن `REQUIRES` باعث خطای زمان بیلد می‌شود:
> `fatal error: driver/foo.h: No such file or directory`.
> فراموش کردن یک فایل در `SRCS` باعث `undefined reference` می‌شود.

### قراردادهای کد

چند مورد که بیشترین تأثیر را دارند:

- **خطاها به‌عنوان مقدار برگردانده می‌شوند** — `core::Result<T>` یا `core::Status`،
  نه `esp_err_t` خام و نه متغیر سراسری. برای بالا بردن خطا از `CORE_TRY_VOID`
  و `CORE_TRY_ASSIGN` استفاده شود.
- **بدون استثنا و بدون RTTI** — `throw`/`try`/`catch` و `dynamic_cast`/`typeid` ممنوع.
- **وابستگی فقط رو به پایین** — `core` هرگز `rtos` یا `drivers` را include نمی‌کند.
- **نوع‌های بین‌لایه‌ای کامل صدا زده می‌شوند** — `core::Result<T>`، نه `Result<T>`.
- هدرهای عمومی در `include/<component>/`، هدرهای داخلی در `detail/`
- هر فایل یک تگ لاگ داشته باشد: `constexpr const char* kTag = "<module>";`
- از `CORE_LOGI/W/E/D/V` استفاده شود، نه `printf` خام و نه `ESP_LOGx` مستقیم
- نام‌گذاری: نوع‌ها `PascalCase`، توابع `snake_case`، اعضای کلاس با `_` انتهایی
  (`handle_`, `pin_`)، ثابت‌ها با پیشوند `k` (`kWaitForever`)؛
  حروف اختصاری مثل کلمه: `I2c`, `Spi`, `Uart`, `Nvs`, `Gpio`
- **واحد در نام می‌آید**: `timeout_ms`, `period_us`, `stack_bytes`
- تخصیص حافظه‌ی پویا در مسیرهای حساس به زمان ممنوع
- `[[nodiscard]]` روی هر تابعی که `Result`/`Status` یا مقدار مهم برمی‌گرداند
- `noexcept` روی هر چیزی که واقعاً نمی‌تواند شکست بخورد

## ۸) مدیریت خطا و لاگ

### مدل خطا — «خطا به‌عنوان مقدار»

چون استثنا در دسترس نیست (بخش ۳)، هر عملیات شکست‌پذیر یک مقدار برمی‌گرداند:

| نوع | معنا |
|---|---|
| `core::Error` | پوشش نازک روی `esp_err_t`؛ کد عددی دست‌نخورده می‌ماند |
| `core::Result<T>` | یا مقدار `T`، یا دلیل نبودنش |
| `core::Status` | موفقیت، یا دلیل شکست (معادل `Result<void>`) |
| `CORE_TRY_VOID(expr)` | اجرا کن؛ اگر شکست خورد خطا را به بالا برگردان |
| `CORE_TRY_ASSIGN(var, expr)` | همان، ولی مقدار را در `var` بگذار (متغیر باید از قبل اعلان شده باشد) |

> ⚠️ `std::expected::value()` در حالت خطا استثنا پرتاب می‌کند که اینجا به
> `std::terminate` می‌رسد. هرگز روی نتیجه‌ای که بررسی نشده `.value()` صدا نزنید.

### سطوح لاگ

| سطح C++ | معادل ESP-IDF | کاربرد |
|---|---|---|
| `CORE_LOGE` | `ESP_LOGE` | خطایی که عملکرد را متوقف می‌کند |
| `CORE_LOGW` | `ESP_LOGW` | وضعیت غیرمنتظره ولی ادامه‌پذیر |
| `CORE_LOGI` | `ESP_LOGI` | رویدادهای مهم (راه‌اندازی، اتصال، تغییر حالت) |
| `CORE_LOGD` | `ESP_LOGD` | جزئیات اشکال‌زدایی (در انتشار خاموش) |
| `CORE_LOGV` | `ESP_LOGV` | پرحجم‌ترین سطح |

- سطح پیش‌فرض فعلی: `INFO` (در `sdkconfig.defaults`)
- سطح را می‌توان در زمان اجرا با `core::set_log_level()` عوض کرد
- در ISR و حلقه‌های پرتکرار لاگ نکن

## ۱۲) گراف دانش پروژه (graphify)

برای اینکه بشود بدون خواندن دستی همه‌ی فایل‌ها به سوال‌های معماری جواب داد، از
ابزار **graphify** استفاده می‌کنیم. خروجی آن در `graphify-out/` است:

| فایل | محتوا |
|---|---|
| `graph.html` | گراف تعاملی — در مرورگر باز کن، سرور لازم نیست |
| `GRAPH_REPORT.md` | گزارش بازرسی: گره‌های اصلی، ارتباطات غافلگیرکننده، سوالات پیشنهادی |
| `graph.json` | داده‌ی خام گراف (مناسب GraphRAG) |
| `manifest.json` | برای به‌روزرسانی افزایشی |

```bash
graphify query "<سوال>"     # پرسیدن از گراف موجود
graphify . --update         # بعد از افزودن یا جابه‌جا کردن فایل‌ها
```

> قاعده‌ی پروژه: قبل از تغییر کد، اول از گراف جهت بگیر. برای سوال‌های
> «فلان چیز به فلان چیز چطور وصل است» حدس نزن — از گراف بپرس.

> ⚠️ نکته‌ی صداقتی: بخشی از یال‌های خام گراف به گره‌هایی اشاره می‌کنند که وجود
> ندارند (نمادهای بیرونی ESP-IDF مثل `esp_err_t` که در کد ما تعریف نشده‌اند).
> این طبیعی است و یعنی گراف «همه‌چیز» را نمی‌داند — مرزهایش همان مرزهای کد ماست.

> ⚠️ `graphify-out/` در گیت نیست: از درخت کد بازتولید می‌شود و فایل‌های داخلی‌اش
> مسیرهای مطلق ماشین دارند.
